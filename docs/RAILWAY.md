# Deploy Health Broget on Railway

Deploy only after final Firebase/Cloudinary configuration and acceptance review. Code push and production deployment are separate operations.

1. Create/select the Railway project and a web service connected to this repository's integration branch. Use the **repository root** as the root directory. The root Dockerfile builds Flutter web and the backend; do not set the old `backend/` Render root/build commands.
2. Generate a public HTTPS domain. Set `PUBLIC_APP_ORIGIN` to that origin without a trailing slash. The API is at `<origin>/api`; readiness is `<origin>/health`.
3. Add variables from `backend/railway.env.example`. Keep the supplied staging database separate from production. MongoDB network access must allow the Railway service, and the cluster must support transactions. Startup creates collections, validators and indexes, so the database user needs those permissions for its application database.
4. Create the new Firebase project on Spark, enable Email/Password, and register Web plus Android (`com.broget.broget_ai`). Add the Railway hostname to Auth authorized domains. Supply matching public project/app/API key values to the web build variables. In Firebase email templates, set the Health Broget application name and allowed action/continue URLs.
5. Put the new private Firebase Admin SDK JSON in the **runtime-only** `FIREBASE_SERVICE_ACCOUNT_JSON` variable. Locally, use `GOOGLE_APPLICATION_CREDENTIALS` pointing to an ignored private file instead. Do not put the Admin private key into public Firebase variables or Docker build arguments.
6. Register the new Web App Check Enterprise/Fraud Defense provider for the Railway domain and set `RECAPTCHA_SITE_KEY`. Register Android App Check using the existing signing certificate and the intended APK/Play distribution requirements. The production API requires valid attestation; do not bypass it to hide configuration failures.
7. Set Cloudinary runtime credentials. Meal uploads use authenticated image delivery and expiring signed download URLs. Verify the account permits these operations using an actual staging upload, display and deletion. No unsigned upload preset is required.
8. Set AI runtime credentials/model with working quota, and optionally USDA_API_KEY for database search. These credentials do not enter the web bundle. Firebase Auth's free tier is independent of AI/hosting/storage costs.
9. Deploy manually. Confirm `/health` returns 200 and `database: mongodb`. Check that startup/cleanup logs contain no credentials. The worker runs within the service, uses leases and retries, and resumes jobs after restart; its execution depends on the Railway service running.
10. Perform acceptance: register, verify email, sign out/in, request and use a password reset, complete onboarding, manually save/edit/delete a meal, scan/review/edit/save a photo meal, verify reports and assistant context, clear chat, change reminder settings, test two-user isolation and delete a disposable test account. Verify Cloudinary files are removed and a failed cleanup retries.
11. Prepare the signed Android release using the new google-services.json and `API_BASE_URL=https://YOUR-SERVICE.up.railway.app/api`. Build with `scripts/build.ps1`; install on a real phone and test login, App Check, camera, gallery, meal review, private photo display and deletion. Preserve the signing key. Only then publish the new APK/download link and arrange cutover from the old site/backend.

Railway supports [Docker build variables](https://docs.railway.com/builds/dockerfiles) and [service variables](https://docs.railway.com/variables). The Dockerfile declares only public Flutter configuration arguments. Never add MongoDB passwords, AI keys, Cloudinary secrets or Firebase Admin JSON as build arguments. The final runtime image runs Node.js 22 as a non-root user.

Railway, Atlas, Cloudinary, Firebase and the AI provider have separate plans and quotas. No guarantee of unlimited free usage is made. Rotate credentials exposed in shared messages before production use.
